Mutualiser le travail

GitHub pour une équipe qui débute

Un seul dépôt partagé, dans une organisation gratuite « biscalab ». C'est un fork public du dépôt amont : on y ajoute un dossier biscalab/ qui contient tout ce qui est à nous, et on ne touche jamais aux fichiers d'Antoine Pirrone. Ainsi le bouton « Sync fork » suffit pour suivre l'amont, sans jamais de conflit.

Fork, pas clone

Un clone est une copie sur un PC. Un fork est une copie sur GitHub, reliée à l'amont, que toute l'équipe partage.

  • Le fork d'un dépôt public est forcément public.
  • Les Issues sont désactivées par défaut dans un fork : cocher Settings → Features → Issues.
  • Au premier clone, GitHub Desktop demande « Comment envisagez-vous d'utiliser cette duplication ? » : répondre « Pour mon propre usage », sinon les pull requests visent le dépôt d'Antoine.
  • Deux forks : Open_Duck_Mini (CAO, docs, STL) et Open_Duck_Mini_Runtime (code du Pi).

Organisation gratuite

  • Plan Free : dépôts publics et privés illimités, Issues, Projects, 2 000 min d'Actions par mois.
  • Création : Paramètres → Organisations → Nouvelle organisation.
  • Au moins deux propriétaires, les autres sont membres.
  • 2FA : obligatoire pour un propriétaire. Appli TOTP (pas de SMS). Le faire ensemble en réunion, imprimer les codes de récupération.
  • GitHub Team est gratuit pour les associations reconnues (GitHub for Nonprofits), mais le plan Free suffit ici.

Tailles et gros fichiers

  • Avertissement au-delà de 50 Mio par fichier, blocage à 100 Mio, 25 Mio maximum par envoi depuis le navigateur.
  • Les STL du canard sont petits : Git LFS est inutile au départ (et sa configuration demande la ligne de commande).
  • GitHub affiche les STL en 3D (< 10 Mo) et les CSV en tableau (< 512 Ko) : pieces.csv devient un tableau consultable en ligne.
  • L'app GitHub Desktop n'a pas de version française ; la documentation officielle, elle, existe en français.

Les 5 gestes GitHub Desktop

  1. Cloner Fichier → Cloner le référentiel. Une seule fois par PC. Choisir « Pour mon propre usage ».
  2. Récupérer Fetch origin puis Pull origin, avant chaque séance. Sans ce geste on travaille sur une version périmée.
  3. Commiter Cocher les fichiers modifiés, écrire un résumé (« Ajoute gabarit zéro servo »), puis Commit to ….
  4. Pousser Push origin, en fin de séance. Tant que ce n'est pas poussé, personne d'autre ne le voit.
  5. Brancher et proposer Current branch → New branch, puis Create Pull Request (ouvre le navigateur). Un référent relit et fusionne.

Le référent fait aussi le Sync fork (page du fork → « Synchroniser la duplication → Mettre à jour la branche ») une fois par mois.

Ce que GitHub nous apporte, par priorité

  1. Issues : une issue = une tâche, avec un responsable et des labels. C'est la liste de choses à faire du projet.
  2. Projects : vue kanban (À faire / En cours / Fait) et vue roadmap par phase, champs personnalisés (Phase, Matériau…).
  3. Milestones : un par phase, pour voir ce qui reste avant le jalon.
  4. Releases : figer un « kit d'impression v1.0 » (jusqu'à 2 Gio par fichier).
  5. Markdown dans docs/ plutôt qu'un wiki séparé : versionné avec le reste. Les Discussions sont superflues pour cinq personnes.
Règle simple pour les fichiers binaires (FCStd, STL, 3MF) : on ne peut pas fusionner deux versions. Celui qui modifie une pièce s'assigne l'issue correspondante : c'est le verrou humain.

Conception

CAO : Onshape, FreeCAD et le modèle physique

La CAO source est un document Onshape public. Nous préférons FreeCAD. Les deux peuvent cohabiter, à condition de savoir ce que chaque outil sait faire, et surtout ce que la simulation attend de nous si une pièce change.

Point clé. L'outil onshape-to-robot, qui produit le modèle physique (MJCF) de la simulation, fonctionne uniquement avec Onshape (clés API, connecteurs dof_* dans l'assemblage). Il ne lit ni FreeCAD ni un STEP. Changer une pièce dans FreeCAD n'est donc pas un problème pour l'imprimer, mais c'en est un pour mettre à jour la simulation.

Onshape

  • Offre gratuite pour usage non commercial ; tous les documents sont publics.
  • « Make a copy » du document amont vers un compte BiscaLab, puis clic droit sur une pièce → Export en STL ou STEP.
  • Collaboration native : plusieurs personnes en même temps, versions immuables, branches et fusion.
  • Garde l'historique paramétrique des pièces amont : une retouche (élargir un passage de câble, épaissir une paroi) reste propre.

Ouvrir le document Onshape amont

FreeCAD 1.0 / 1.1

  • 1.0 (nov. 2024) corrige le nommage topologique et intègre un atelier Assembly natif ; 1.1 (mars 2026) améliore PartDesign, Assembly et FEM.
  • Un import STEP ne donne qu'un solide sans historique : parfait pour une pièce nouvelle ou un gabarit, moins pour retoucher une pièce amont.
  • Le .FCStd est un zip : git ne sait pas le comparer, chaque version est une copie complète. Régler Préférences → Général → Document → compression = 0 et renseigner le nom d'auteur.
  • Ignorer *.FCBak. Un seul éditeur par fichier. Toujours exporter un STEP à côté du FCStd.
  • Extension RobotCAD (OVERCROSS) : exporte de l'URDF/SDF avec masses calculées, pas de MJCF.

Trois options pour le modèle physique

Le modèle MJCF contient, pour chaque corps, masse, centre de masse et inertie. Le projet remplace la masse Onshape par l'estimation du slicer, à cause du remplissage à 15 %. Si nous changeons matériau, remplissage ou pièce, ces valeurs changent.

A · Rester sur Onshape

Copier le document, modifier les surcharges de masse des pièces, réexporter avec onshape-to-robot, puis refaire les retouches manuelles (body base, site imu en (−0,08 ; 0 ; 0,05), joints *_backlash, keyframe home). Un STEP s'importe dans Onshape, mais il faut recréer l'assemblage et ses connecteurs.

B · Corriger le MJCF à la main recommandé

Obtenir masse, centre de masse et inertie des pièces modifiées : dans FreeCAD (Shape.Volume, CenterOfMass, MatrixOfInertia × densité), par la masse annoncée par PrusaSlicer, ou en pesant. Recomposer l'<inertial> de chaque body (théorème de Huygens). Reporter les mêmes valeurs dans l'URDF de Placo.

C · RobotCAD

Exporter un URDF depuis FreeCAD, le convertir en MJCF (compile de MuJoCo), puis redonner tous les noms attendus par le code (trunk_assembly, sites left_foot/right_foot, geoms *_foot_bottom_tpu, classe sts3215). Faisable, mais long et fragile.

Piège repéré dans le code. Le fichier joints_properties.xml actuel ne contient pas les valeurs de l'entraînement de référence (kp 17,8 contre 17,11 dans le modèle backlash). Un réexport ne redonne donc pas les paramètres d'origine : partir du modèle open_duck_mini_v2_backlash.xml et n'y toucher que les inertiels.
