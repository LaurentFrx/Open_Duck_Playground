Ce qui ne se négocie pas

La politique de marche fournie suppose exactement ceci. Tout écart impose un réentraînement.

  • Servos STS3215 7,4 V, rapport 1/345 (réf. C001, « 19 kg·cm ») — pas la 12 V, pas les rapports 1/191 ni 1/147.
  • Batterie 2S (2 × 18650 haute décharge ≥ 25 A) — jamais 3S.
  • Semelles en TPU à 40 % : c'est le seul contact modélisé avec le sol.
  • Géométrie identique aux STL amont, masses à ±10 % près.
  • Gain P = 30, boucle 50 Hz, action_scale 0,25.
Comprendre pourquoi

Les 5 règles d'or

  1. Si ce n'est pas sur GitHub (issue ou journal), ça n'existe pas. Signal sert à discuter, GitHub à décider.
  2. Pull en arrivant, Push en partant. Un fichier CAO n'a qu'un éditeur à la fois : celui qui s'est assigné l'issue.
  3. On ne modifie jamais un fichier amont : on le copie dans biscalab/, puis on le modifie.
  4. Pas de phase suivante, ni d'achat suivant, sans fiche de test validée.
  5. Sécurité non négociable : batterie jamais en charge sans surveillance, laser jamais seul, matériaux interdits affichés.

Décisions à trancher

  • Chargeur « TP4056 2S » du plan d'achats : le TP4056 est un chargeur 1S. Choisir un vrai chargeur 2S équilibré (ou charger hors robot via le BMS et un chargeur 8,4 V).
  • Calibre du BMS : à fixer après la mesure du courant crête en phase 5.
  • Carte Waveshare : sa fiche annonce une entrée 9 à 12,6 V ; le canard l'alimente en 2S (7,4 V). Vérifier sur le banc avant d'acheter les 12 servos restants.
  • Outil CAO : retouches de pièces amont dans une copie Onshape, pièces nouvelles dans FreeCAD — à valider en réunion.
  • GPU pour réentraîner : qui dispose d'une carte NVIDIA (CUDA 12) ? Sinon, location cloud ponctuelle.
  • Hébergement de ce dossier : lien partagé ou PWA installable sur un sous-domaine.

Présentation

Open Duck Mini V2

Réplique miniature et stylisée « canard » du droïde BDX de Disney, développée par Antoine Pirrone (Pollen Robotics / équipe Rhoban, Bordeaux) et Grégoire Passault, avec le soutien de Hugging Face. Code, CAO et politiques de marche sont publiés sous licence Apache-2.0.

Comment il marche

Un réseau de neurones (politique PPO, 101 entrées → 14 sorties) est entraîné dans le simulateur MuJoCo à imiter des trajectoires de marche générées par Placo. Exporté en ONNX, il tourne à 50 Hz sur le Pi Zero : il lit l'IMU, les positions des servos et les contacts de pied, et renvoie les consignes des 14 articulations.

Qu'il soit piloté à la manette ou autonome, le robot gère seul son équilibre. Seule la décision de direction change de main.

v1, V2, Microduck

  • v1 « mini_BDX » (35 cm, Dynamixel, Isaac Gym) : abandonnée, trop de jeu aux articulations.
  • V2 (branche v2 des dépôts) : la version à reproduire. Objectif BOM < 400 $.
  • Microduck (Pollen × Hugging Face, août 2026) : produit commercial de 25 cm issu d'Open Duck Mini, 399 $, matériel non publié. Son dépôt RL est une source d'idées, pas un modèle à copier.

GitHub pour une équipe qui débute

Un seul dépôt partagé, dans une organisation gratuite « biscalab ». C'est un fork public du dépôt amont : on y ajoute un dossier biscalab/ qui contient tout ce qui est à nous, et on ne touche jamais aux fichiers d'Antoine Pirrone. Ainsi le bouton « Sync fork » suffit pour suivre l'amont, sans jamais de conflit.

Fork, pas clone

Un clone est une copie sur un PC. Un fork est une copie sur GitHub, reliée à l'amont, que toute l'équipe partage.

  • Le fork d'un dépôt public est forcément public.
  • Les Issues sont désactivées par défaut dans un fork : cocher Settings → Features → Issues.
  • Au premier clone, GitHub Desktop demande « Comment envisagez-vous d'utiliser cette duplication ? » : répondre « Pour mon propre usage », sinon les pull requests visent le dépôt d'Antoine.
  • Deux forks : Open_Duck_Mini (CAO, docs, STL) et Open_Duck_Mini_Runtime (code du Pi).

Organisation gratuite

  • Plan Free : dépôts publics et privés illimités, Issues, Projects, 2 000 min d'Actions par mois.
  • Création : Paramètres → Organisations → Nouvelle organisation.
  • Au moins deux propriétaires, les autres sont membres.
  • 2FA : obligatoire pour un propriétaire. Appli TOTP (pas de SMS). Le faire ensemble en réunion, imprimer les codes de récupération.
  • GitHub Team est gratuit pour les associations reconnues (GitHub for Nonprofits), mais le plan Free suffit ici.

Tailles et gros fichiers

  • Avertissement au-delà de 50 Mio par fichier, blocage à 100 Mio, 25 Mio maximum par envoi depuis le navigateur.
  • Les STL du canard sont petits : Git LFS est inutile au départ (et sa configuration demande la ligne de commande).
  • GitHub affiche les STL en 3D (< 10 Mo) et les CSV en tableau (< 512 Ko) : pieces.csv devient un tableau consultable en ligne.
  • L'app GitHub Desktop n'a pas de version française ; la documentation officielle, elle, existe en français.

Les 5 gestes GitHub Desktop

  1. Cloner Fichier → Cloner le référentiel. Une seule fois par PC. Choisir « Pour mon propre usage ».
  2. Récupérer Fetch origin puis Pull origin, avant chaque séance. Sans ce geste on travaille sur une version périmée.
  3. Commiter Cocher les fichiers modifiés, écrire un résumé (« Ajoute gabarit zéro servo »), puis Commit to ….
  4. Pousser Push origin, en fin de séance. Tant que ce n'est pas poussé, personne d'autre ne le voit.
  5. Brancher et proposer Current branch → New branch, puis Create Pull Request (ouvre le navigateur). Un référent relit et fusionne.

Le référent fait aussi le Sync fork (page du fork → « Synchroniser la duplication → Mettre à jour la branche ») une fois par mois.

Ce que GitHub nous apporte, par priorité

  1. Issues : une issue = une tâche, avec un responsable et des labels. C'est la liste de choses à faire du projet.
  2. Projects : vue kanban (À faire / En cours / Fait) et vue roadmap par phase, champs personnalisés (Phase, Matériau…).
  3. Milestones : un par phase, pour voir ce qui reste avant le jalon.
  4. Releases : figer un « kit d'impression v1.0 » (jusqu'à 2 Gio par fichier).
  5. Markdown dans docs/ plutôt qu'un wiki séparé : versionné avec le reste. Les Discussions sont superflues pour cinq personnes.
Règle simple pour les fichiers binaires (FCStd, STL, 3MF) : on ne peut pas fusionner deux versions. Celui qui modifie une pièce s'assigne l'issue correspondante : c'est le verrou humain.

Conception

CAO : Onshape, FreeCAD et le modèle physique

La CAO source est un document Onshape public. Nous préférons FreeCAD. Les deux peuvent cohabiter, à condition de savoir ce que chaque outil sait faire, et surtout ce que la simulation attend de nous si une pièce change.

Point clé. L'outil onshape-to-robot, qui produit le modèle physique (MJCF) de la simulation, fonctionne uniquement avec Onshape (clés API, connecteurs dof_* dans l'assemblage). Il ne lit ni FreeCAD ni un STEP. Changer une pièce dans FreeCAD n'est donc pas un problème pour l'imprimer, mais c'en est un pour mettre à jour la simulation.

Onshape

  • Offre gratuite pour usage non commercial ; tous les documents sont publics.
  • « Make a copy » du document amont vers un compte BiscaLab, puis clic droit sur une pièce → Export en STL ou STEP.
  • Collaboration native : plusieurs personnes en même temps, versions immuables, branches et fusion.
  • Garde l'historique paramétrique des pièces amont : une retouche (élargir un passage de câble, épaissir une paroi) reste propre.

Ouvrir le document Onshape amont

FreeCAD 1.0 / 1.1

  • 1.0 (nov. 2024) corrige le nommage topologique et intègre un atelier Assembly natif ; 1.1 (mars 2026) améliore PartDesign, Assembly et FEM.
  • Un import STEP ne donne qu'un solide sans historique : parfait pour une pièce nouvelle ou un gabarit, moins pour retoucher une pièce amont.
  • Le .FCStd est un zip : git ne sait pas le comparer, chaque version est une copie complète. Régler Préférences → Général → Document → compression = 0 et renseigner le nom d'auteur.
  • Ignorer *.FCBak. Un seul éditeur par fichier. Toujours exporter un STEP à côté du FCStd.
  • Extension RobotCAD (OVERCROSS) : exporte de l'URDF/SDF avec masses calculées, pas de MJCF.

Trois options pour le modèle physique

Le modèle MJCF contient, pour chaque corps, masse, centre de masse et inertie. Le projet remplace la masse Onshape par l'estimation du slicer, à cause du remplissage à 15 %. Si nous changeons matériau, remplissage ou pièce, ces valeurs changent.

A · Rester sur Onshape

Copier le document, modifier les surcharges de masse des pièces, réexporter avec onshape-to-robot, puis refaire les retouches manuelles (body base, site imu en (−0,08 ; 0 ; 0,05), joints *_backlash, keyframe home). Un STEP s'importe dans Onshape, mais il faut recréer l'assemblage et ses connecteurs.

B · Corriger le MJCF à la main recommandé

Obtenir masse, centre de masse et inertie des pièces modifiées : dans FreeCAD (Shape.Volume, CenterOfMass, MatrixOfInertia × densité), par la masse annoncée par PrusaSlicer, ou en pesant. Recomposer l'<inertial> de chaque body (théorème de Huygens). Reporter les mêmes valeurs dans l'URDF de Placo.

C · RobotCAD

Exporter un URDF depuis FreeCAD, le convertir en MJCF (compile de MuJoCo), puis redonner tous les noms attendus par le code (trunk_assembly, sites left_foot/right_foot, geoms *_foot_bottom_tpu, classe sts3215). Faisable, mais long et fragile.

Piège repéré dans le code. Le fichier joints_properties.xml actuel ne contient pas les valeurs de l'entraînement de référence (kp 17,8 contre 17,11 dans le modèle backlash). Un réexport ne redonne donc pas les paramètres d'origine : partir du modèle open_duck_mini_v2_backlash.xml et n'y toucher que les inertiels.

Paramètres d'impression documentés

  • Toutes les pièces en PLA standard, 15 % de remplissage. Seule exception : foot_bottom_tpu.stl en TPU à 40 %.
  • Orientation, supports et hauteur de couche ne sont pas documentés par l'amont. Nous les fixerons nous-mêmes, pièce par pièce, et les figerons dans un projet 3MF par plateau.
  • La première version suit l'amont à la lettre : la politique de marche a été entraînée avec les masses de ces réglages.

Inserts M3 à chaud

  1. Acheter les inserts listés dans la BOM amont : les trous de la CAO sont dimensionnés pour eux. Faire d'abord une pièce test.
  2. Trou droit, sans cône, environ 1 mm plus profond que l'insert.
  3. Fer réglé 10 à 20 °C au-dessus de la température d'impression (≈ 225 °C pour le PLA, ≈ 245 °C pour le PETG). Le Pinecil V2 du FabLab convient avec une panne adaptée.
  4. Enfoncer l'insert à 90 % avec le fer, finir avec un outil plat et maintenir quelques secondes, bien perpendiculaire.

Feetech STS3215 : la bonne référence

VersionCoupleVitesse à videCourant bloquéVerdict
7,4 V · 1/345 (C001)19,5 kg·cm52 tr/min2,5 Ala bonne
7,4 V · 1/191 (C044), 1/147 (C046)moindreplus rapide—à éviter : hors modèle BAM
12 V · 30 kg·cm30 kg·cm45 tr/min2,7 Aà éviter : pas de paramètres BAM, pied qui ne se lève plus assez (issue #52)
  • Série TTL half-duplex, 1 Mbit/s, ID 0 à 253, codeur magnétique 12 bits (4096 pas/tour, 0,088°).
  • Protections firmware : coupure à 70 °C, surintensité > 2 A pendant 2 s, blocage > 80 % pendant 2 s. La boucle de marche ne surveille ni courant ni température.
  • Plage de tension : 4 à 7,4 V selon Waveshare, 5 à 8,4 V selon Seeed. Un pack 2S chargé fait 8,4 V : prévoir la mesure sur le banc.
  • Firmware : des sous-versions différentes entre servos provoquent « Parsing error in set_kps() » (issue Runtime #26). Mise à jour uniquement par le logiciel Feetech sous Windows. Acheter les 14 du même lot limite le risque.

IMU BNO055

  • Mode NDOF (fusion 9 axes). Le runtime lit gyroscope et accéléromètre à 50 Hz, sans filtrage ; il n'utilise pas le quaternion.
  • Problème connu : la BNO055 fait du « clock stretching » I²C que le Raspberry Pi gère mal. Remèdes documentés : passer en UART (broche PS1 au 3,3 V) ou ralentir le bus (dtparam=i2c_arm_baudrate=10000). Le projet n'a pas tranché ; le code UART est commenté.
  • Calibration par calibrate_imu.py → imu_calib_data.pkl dans le dossier courant. Lancer la marche depuis ce dossier.
  • Surveiller les messages [IMU]: dans la console.

Alimentation

  • Pack 2S : 6,8 V vide → 8,4 V plein. Le modèle de simulation est identifié à 7,4 V : couple et gain varient de +13,5 % à 8,4 V et −8 % à 6,8 V.
  • Charger les deux cellules à la même tension avant de les mettre dans le support.
  • Chute de tension sous charge = erreurs CRC sur le bus (issue #49) : cellules ≥ 25 A, câbles courts et de bonne section, XT30.
  • Banc d'essai : alimentation de laboratoire 7,4 V limitée en courant (3 A pour un servo, 10 A pour le robot complet) avant la batterie.
  • La carte Waveshare transmet la tension d'entrée directement aux servos : ne jamais la brancher sur 12 V avec des servos 7,4 V.

Sécurité Li-ion

  • Charge sur surface incombustible, dans un sac ou une boîte ignifuge, jamais sans surveillance.
  • Arrêter si une cellule chauffe, gonfle ou sent.
  • Stockage à ≈ 50 % de charge, hors du robot, dans une boîte métallique.
  • Consigne incendie : évacuer ; n'intervenir que formé, avec un moyen d'extinction adapté (sable, extincteur classe D ou eau en grande quantité).
  • Ne jamais court-circuiter une 18650 : les pôles nus sont à protéger pendant le montage.

Le dépôt Open_Duck_Mini_Runtime (branche v2) contient tout ce qui tourne sur le robot : la boucle de marche, les scripts de configuration des servos, la calibration de l'IMU et des offsets, et le pilotage à la manette. Une image système prête à flasher évite l'installation manuelle.

Le cœur du sujet

Marche, calibration et transfert sim → réel

La marche n'est pas programmée : elle est apprise en simulation, puis exécutée telle quelle sur le robot. La politique a donc « mémorisé » un robot précis — ses masses, ses servos, ses semelles, son jeu mécanique. Cette page dit ce qui est figé, ce qui se règle sans réentraîner, et ce qui impose de repasser par la simulation.

Se règle sans réentraîner

  • Les ID des servos et l'alignement des palonniers (offsets).
  • La calibration et l'orientation de l'IMU (imu_upside_down).
  • De petites variations de masse, de l'ordre de ±10 % par corps.
  • La fréquence de pas (phase_frequency_factor_offset, croix de la manette).

Impose un réentraînement

  • Toute modification de cinématique (longueur de segment, axe, écartement, forme du pied).
  • Un autre servo (12 V, autre rapport), un autre gain P, une batterie 3S.
  • Une autre semelle que le TPU (frottement différent).
  • Une redistribution importante de la masse (tête, batterie déplacée, calculateur plus lourd).

Ce que la politique a figé

  • Masses et inerties du MJCF (2,107 kg au total).
  • Un modèle de servo STS3215 7,4 V identifié avec BAM : kp 17,11, couple max ±3,23 N·m, damping 0,56, frottement 0,068, armature 0,027.
  • Un sol de frottement 0,6, un jeu de ±0,5° sur les jambes.
  • La pose « home », une période de marche de 0,54 s (27 pas à 50 Hz).

La politique fournie, telle quelle : conditions

Documenté : elle fonctionne sur un robot « built to the standard specs ». Aucune tolérance chiffrée n'est publiée.

  • 14 degrés de liberté dans le même ordre, mêmes signes et zéros, même pose home.
  • 50 Hz, action_scale 0,25, gain P = 30.
  • STS3215 7,4 V au rapport 1/345.
  • Batterie 2S, semelles en TPU, IMU dans un repère compatible.
  • Le pkl fourni (période 0,54 s) à côté du script.
Test gratuit avant de construire (CPU, pas de GPU) : modifier les masses dans le MJCF selon nos pièces réelles, puis uv run playground/open_duck_mini_v2/mujoco_infer.py -o BEST_WALK_ONNX_2.onnx. Si le canard simulé tient debout et marche, nos écarts sont dans la tolérance.

Réentraîner, si nécessaire

  1. Matériel : GPU NVIDIA avec CUDA 12 (jax[cuda12]), Python ≥ 3.11, uv. Un CPU seul n'est documenté nulle part comme viable. Repère : 300 M pas en 1 h 11 sur RTX 3090.
  2. Références (si la géométrie change) : uv run scripts/auto_waddle.py -j8 --duck open_duck_mini_v2 --sweep puis fit_poly.py → polynomial_coefficients.pkl, copié dans playground/open_duck_mini_v2/data/ et à côté du script du runtime.
  3. Modèle : partir de open_duck_mini_v2_backlash.xml (kp 17,11), corriger les inertiels. Corriger aussi FLOOR_GEOM_ID (46) et TORSO_BODY_ID (2) dans randomize.py, sinon la randomisation du sol et du tronc ne fait rien.
  4. Entraînement : uv run playground/open_duck_mini_v2/runner.py --task flat_terrain_backlash --num_timesteps 300000000. Export ONNX automatique à chaque checkpoint.
  5. Validation : mujoco_infer.py, puis sur le robot suspendu, puis au sol avec la potence.

Sans GPU au FabLab : location horaire d'une instance GPU (quelques euros l'heure) ou le PC d'un membre. À trancher en phase 0.

Recommandations pour BiscaLab

  1. Acheter des STS3215 C001 7,4 V 1/345, alimenter en 2S, imprimer les semelles en TPU 40 % et respecter strictement la géométrie amont.
  2. Peser chaque sous-ensemble et comparer aux masses du MJCF (tronc 0,699 kg ; tête + cou 0,582 kg ; jambe ≈ 0,41 kg ; total 2,107 kg). Noter les écarts dans la fiche de test.
  3. Ne découper au laser que des pièces non structurelles ou de l'outillage ; si une pièce du robot change, corriger son inertiel.
  4. Avant toute construction, tester la politique fournie sur le MJCF corrigé avec mujoco_infer.py. C'est gratuit et ça lève le doute.
  5. Réentraîner seulement si le test tombe ou si l'on change servo, semelle, tension ou géométrie — avec les deux indices corrigés dans randomize.py et le modèle backlash (kp 17,11).
  6. Garder le filtre passe-bas désactivé, le gain P à 30 et la boucle sous 20 ms : trois réglages « innocents » qui cassent le transfert.

Batteries

  • Charge : surface incombustible, sac ou boîte ignifuge, présence humaine, arrêt si chauffe ou gonflement.
  • Stockage : ≈ 50 %, hors robot, boîte métallique, pôles protégés.
  • Incendie : évacuer, n'intervenir que formé et équipé.

Laser xTool P2S

  • Jamais seul, jamais sans extraction.
  • Matériaux interdits affichés : PVC, vinyle, ABS, polycarbonate, polystyrène, fibre de carbone enduite.
  • Extincteur CO₂ à portée ; surveiller les découpes d'acrylique.

Banc et robot

  • Alimentation labo limitée en courant tant que la batterie n'est pas validée.
  • Robot sur support ou potence pour tout script qui bouge ; mains hors des articulations.
  • Bouton A (pause) toujours à portée pendant une marche.

Glossaire

Fork / clone
Copie du dépôt sur GitHub (partagée) / copie sur un PC (locale).
Commit / push / pull
Enregistrer une version / l'envoyer sur GitHub / récupérer celles des autres.
Issue
Une tâche, un problème ou une question, avec un responsable.
Pull request
Proposition de modification relue avant fusion.
Milestone
Jalon : un groupe d'issues à boucler avant une date.
STL / STEP / 3MF
Maillage pour imprimer / géométrie exacte pour la CAO / projet d'impression complet.
Kerf
Largeur de matière brûlée par le laser (0,1 à 0,25 mm), à compenser.
Insert à chaud
Écrou laiton fondu dans le plastique pour visser en M3.
Servo bus série
Servo adressable (ID) chaîné sur un seul câble, avec retour de position.
IMU
Centrale inertielle : gyroscope + accéléromètre (+ magnétomètre), donne l'attitude.
BMS / UBEC
Protection et équilibrage du pack / régulateur 5 V à découpage.
2S
Deux cellules en série (7,4 V nominal, 8,4 V chargé).
RL / PPO
Apprentissage par renforcement / l'algorithme utilisé pour entraîner la marche.
Politique
Le réseau de neurones qui, à partir des capteurs, décide des consignes des servos.
MuJoCo / MJCF
Le simulateur physique / son format de modèle de robot (XML).
URDF
Autre format de modèle de robot, utilisé par Placo.
ONNX
Format d'échange du réseau entraîné, exécuté par onnxruntime sur le Pi.
Sim2real
Le passage de la simulation au robot réel, et tout ce qui peut y casser.
Domain randomization
Varier masses, frottements, gains pendant l'entraînement pour rendre la politique tolérante.
BAM
Méthode Rhoban d'identification d'un servo (gain, couple, frottements) pour la simulation.
Offsets
Écart entre le zéro mécanique réel et le zéro du servo, mesuré robot par robot.
Keyframe « home »
La posture de référence, debout, d'où partent toutes les consignes.
